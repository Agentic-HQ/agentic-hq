# Research Notes: Alternatives to Homa + Benchmarks/Success Metrics

**Date:** 2026-07-23. **Audience:** knows C and basic networking, not a networking specialist.
**Scope:** Part A = alternatives to the Homa datacenter transport ([SIGCOMM'18 paper](https://dl.acm.org/doi/10.1145/3230543.3230564), [Linux kernel module](https://github.com/PlatformLab/HomaModule), [ATC'21 paper](https://www.usenix.org/conference/atc21/presentation/ousterhout)). Part B = how this space measures success, plus published Homa-vs-TCP results and criticisms.

**Method note:** USENIX/ACM PDF servers block automated fetches, but the full PDF binaries of the ATC'21 Homa paper, the SIGCOMM'18 Homa paper (arXiv complete version), eRPC, Demikernel, and dcPIM papers were downloaded and text-extracted locally, so the numbers below marked with those papers come from the primary text, not summaries.

---

## Quick orientation: what Homa is (baseline for comparison)

Homa is a **receiver-driven, message-oriented (RPC-based), connectionless** datacenter transport. Receivers schedule most inbound data by sending explicit GRANTs and use commodity-switch **priority queues** to approximate SRPT (shortest-remaining-processing-time-first), which favours short messages ([SIGCOMM'18 paper](https://people.csail.mit.edu/alizadeh/papers/homa-sigcomm18.pdf), [LWN part 2](https://lwn.net/Articles/914030/)). Headline claims:

- Research (kernel-bypass, RAMCloud) implementation: **P99 round-trip < 15 µs for short messages on a 10 Gbps network at 80% load**, ~100x lower than the best previously published implementation measurements ([arXiv complete version, abstract](https://arxiv.org/abs/1803.09615)).
- Linux kernel module on a 40-node, 25 Gbps cluster: **P99 tail latency for short messages 7–83x lower than TCP and DCTCP** ([ATC'21 PDF](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

# Part A — Alternatives

## A1. Plain kernel TCP in the datacenter (the incumbent baseline)

**What it is:** the default Linux in-kernel TCP stack — what virtually all datacenter RPC systems (gRPC, Thrift, HTTP APIs, memcached, etc.) actually run on today ([LWN: Moving past TCP in the data center, part 1](https://lwn.net/Articles/913260/)).

**Published numbers (with context):**

- **Small-RPC RTT:** 100-byte request/response over kernel TCP measured **23.4 µs median** end-to-end at application level, on CloudLab xl170 nodes (Xeon E5-2640v4, 10 cores/2.4 GHz, Mellanox ConnectX-4 25 GbE, one switch, Linux 5.4.80, MTU 3000) under best-case (unloaded) conditions ([ATC'21, Table 2](https://www.usenix.org/system/files/atc21-ousterhout.pdf)). On an older 10 GbE CloudLab cluster the best-case 100 B kernel-TCP RPC was **15.5 µs** ([Homa SIGCOMM'18, complete version](https://arxiv.org/pdf/1803.09615)). The eRPC authors note the "widely-believed" kernel-networking latency figure of 10–100 µs ([eRPC NSDI'19 paper](https://www.usenix.org/conference/nsdi19/presentation/kalia)).
- **Messages/sec:** a whole 20-hyperthread xl170 node maxed out at about **1.0 M small RPCs/sec** as client or server (multiple threads, many concurrent RPCs, 25 GbE, 2021) ([ATC'21, Table 2](https://www.usenix.org/system/files/atc21-ousterhout.pdf)). Ousterhout's Netdev keynote put it as: TCP delivers ~1 M short messages/sec where hardware should support 10–100 M ([LWN part 1](https://lwn.net/Articles/913260/)).
- **Throughput/core:** on 100 GbE hardware the Linux TCP stack achieves roughly **~42 Gbps per core** for bulk transfer, with the receiver-side kernel-to-user data copy as the dominant bottleneck ([Understanding Host Network Stack Overheads, SIGCOMM'21](https://www.cs.cornell.edu/~ragarwal/pubs/network-stack.pdf)). Single-stream 500 KB messages: **20.3 Gbps** on the 25 GbE ATC'21 testbed ([ATC'21, Table 2](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

**Deployment requirements:** none — it is the incumbent; works over any IP network, any NIC, unmodified apps.

**Key limitations:** stream orientation (application must add message framing), per-connection state (~2000 bytes each on Linux), fair-share scheduling (all connections finish slowly), sender-driven congestion control reacting to buffer buildup, and in-order delivery forcing flow-consistent routing ([LWN part 1](https://lwn.net/Articles/913260/)). Measured tail behaviour: at P99, two-thirds of slow short TCP RPCs were stuck behind a long message on the same stream (head-of-line blocking) and the rest were buffer buildup in NIC/switch ([ATC'21 §5.2](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

## A2. Datacenter-tuned TCP: DCTCP and BBR

**DCTCP** (SIGCOMM 2010, [ACM DOI](https://dl.acm.org/doi/10.1145/1851182.1851192)) keeps switch queues short by using ECN marks proportionally rather than as a binary loss signal. It is what Homa papers use as the "tuned datacenter TCP" comparison.

- What it fixes: queue occupancy (buffer buildup), so large-message congestion behaviour is much better than plain TCP; in the ATC'21 buffer tests DCTCP showed no degradation until switch buffer space fell below **2 MB**, versus TCP degrading below 10 MB ([ATC'21 §5.5](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).
- What it does NOT fix: short-message tail latency. On the ATC'21 cluster benchmark, **Homa's P99 for short messages was 7–83x lower than DCTCP** (and DCTCP's own short-message latency varied **7x across a 10x load change**, vs <2x for Homa) ([ATC'21 §5.2, §5.4](https://www.usenix.org/system/files/atc21-ousterhout.pdf)). The stream/connection/fair-sharing problems of TCP are unchanged — it's still TCP.
- Deployment: needs ECN marking configured on switches (marking threshold 70 KB in the ATC'21 setup) and kernel support (`tcp_congestion_control=dctcp`); safe only inside the datacenter ([ATC'21 §5](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

**BBR** ([ACM Queue 2016, "BBR: Congestion-Based Congestion Control"](https://queue.acm.org/detail.cfm?id=3022184)) is a Google congestion-control algorithm that estimates bottleneck bandwidth and RTT instead of reacting to loss. It targets long, high-BDP paths (WAN, YouTube egress, edge). It changes nothing about TCP's stream/message and connection model, and it is not what hyperscalers use for intra-datacenter RPC — Google's own datacenter answer was TIMELY then **Swift** (delay-based CC inside their Snap userspace stack; see A5) ([Swift SIGCOMM'20](https://research.google/pubs/swift-delay-is-simple-and-effective-for-congestion-control-in-the-datacenter/)). Treat BBR as "wrong layer, wrong problem" for short-RPC tail latency: it tunes how a byte stream fills a pipe, not how a 200-byte RPC dodges a queue.

## A3. RDMA: InfiniBand, RoCEv2, iWARP — and AWS SRD as a related approach

**What it is:** the NIC implements a reliable transport in hardware; applications post send/recv/read/write "verbs" and the NIC DMAs data directly to/from user memory, bypassing the kernel.

**Typical latencies and message rates:**

- RDMA read latency between two hosts under one ToR switch: **1.7 µs (ConnectX-3, 56 Gbps InfiniBand), 2.0 µs (ConnectX-5, Ethernet), 2.9 µs (ConnectX-4, 25 GbE)** — measured medians, 32 B ops, 2019 ([eRPC NSDI'19, Table 2](https://www.usenix.org/conference/nsdi19/presentation/kalia)).
- RAMCloud's InfiniBand transport (kernel bypass, reliable connected QPs): best-case **3.9 µs** for a 100 B RPC, ~2016-era FDR gear ([Homa SIGCOMM'18](https://arxiv.org/pdf/1803.09615)).
- Modern hardware message rates: NVIDIA ConnectX-7 (400 Gbps) datasheet: **330–370 million messages/sec** ([NVIDIA ConnectX-7 datasheet](https://www.nvidia.com/content/dam/en-zz/Solutions/networking/infiniband-adapters/infiniband-connectx7-data-sheet.pdf)). That is hardware verbs rate — three orders of magnitude above kernel TCP's ~1 M RPCs/sec/node above.

**The PFC problem (RoCEv2):** RoCEv2 runs the InfiniBand transport over UDP/IP on Ethernet, but historically demanded a *lossless* fabric via Priority Flow Control. Microsoft's deployment paper documents what that costs at scale: **PFC-induced deadlocks ("yes, it happened!"), NIC pause-frame storms, and RDMA transport livelock**, mitigated with DSCP-based PFC plus the DCQCN congestion-control scheme in NIC firmware ([RDMA over Commodity Ethernet at Scale, SIGCOMM'16](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/rdma_sigcomm2016.pdf)). Also, RDMA's connected mode is still stream-like per queue pair: with one connection per client-server pair, RAMCloud measured tail latencies **~1000x worse than Homa** for small messages due to head-of-line blocking behind large messages ([Homa SIGCOMM'18 §5.1](https://arxiv.org/pdf/1803.09615)).

**iWARP, briefly:** RDMA layered on top of full TCP offload in the NIC. It tolerates lossy networks but requires a much more complex NIC (a TCP stack in silicon) and lost the market to RoCE; it survives mainly in niche storage gear ([Datacenter Ethernet and RDMA: Issues at Hyperscale, arXiv 2023](https://arxiv.org/pdf/2302.03337)).

**AWS SRD / EFA (related approach):** SRD ("Scalable Reliable Datagram") is AWS's cloud-built alternative: implemented in the **Nitro card**, it deliberately drops in-order delivery, **sprays packets across many network paths simultaneously**, and delivers out of order, letting the layer above (libfabric/MPI/NCCL) reorder — eliminating both PFC and head-of-line blocking ([A Cloud-Optimized Transport Protocol for Elastic and Scalable HPC, IEEE Micro 2020](https://ieeexplore.ieee.org/document/9167399/), [PDF mirror](https://saeed.github.io/CS8803_DNS_Spring2024/assets/srd.pdf)). Exposed as the EFA device on EC2; AWS materials quote **~15.5 µs MPI ping-pong latency** for EFA (c5n-era instances, 100 Gbps, 2019-2020) ([EFA notes/quote](https://www.ernestchiang.com/en/notes/general/aws-srd-scalable-reliable-datagram/), [AWS EFA docs](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/efa.html)) — higher latency than raw RDMA on-prem, but with cloud-scale multipathing and no lossless-fabric requirement.

**Deployment requirements (RDMA family):** RDMA-capable NICs on every host; for RoCEv2 either PFC-configured lossless Ethernet + DCQCN or newer loss-tolerant NICs; application rewrite to verbs (or an RPC library on top); careful operational monitoring (the entire SIGCOMM'16 paper is a war-story catalogue) ([Microsoft SIGCOMM'16](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/rdma_sigcomm2016.pdf)).

## A4. Kernel-bypass user-space stacks (DPDK-class)

**eRPC (NSDI'19) — the reference point for software RPC speed.** A general-purpose RPC library over DPDK (lossy Ethernet) or InfiniBand, using polling, zero-copy buffers, and congestion control (Timely/DCQCN-style) in userspace ([paper page](https://www.usenix.org/conference/nsdi19/presentation/kalia), [arXiv](https://arxiv.org/abs/1806.00680), [GitHub](https://github.com/erpc-io/eRPC)). Exact numbers from the paper:

- **Median RPC latency 2.3 µs** (32 B RPCs, ConnectX-5 Ethernet cluster, same ToR switch, 2019) — at most **800 ns worse than a raw RDMA read** on the same hardware ([eRPC Table 2](https://www.usenix.org/conference/nsdi19/presentation/kalia)).
- **Up to 10 M small RPCs/sec per core**: each thread simultaneously *issues* ~5 M requests/sec and *serves* ~5 M/sec with request batch B=3 on ConnectX-4 25 GbE; 4.96 Mrps issued with congestion control on, 5.44 Mrps with it off (9% CC overhead) ([eRPC §6.2](https://www.usenix.org/conference/nsdi19/presentation/kalia)).
- **Large messages: 75 Gbps with one core** (8 MB messages, two nodes on 100 Gbps ConnectX-5 InfiniBand; rises to 92 Gbps if the server-side memcpy is commented out) ([eRPC §6.4](https://www.usenix.org/conference/nsdi19/presentation/kalia)).
- Scale: 100-node lossy-Ethernet cluster, 10 threads/node → **12.3 Mrps per node** and **99.99th-percentile latency < 700 µs** with up to ~20,000 sessions per node ([eRPC §6.3](https://www.usenix.org/conference/nsdi19/presentation/kalia)).
- **Raft 3-way replication in 5.5 µs** on lossy Ethernet, unmodified production Raft library ([eRPC abstract](https://arxiv.org/abs/1806.00680)).
- Caveats: performance collapses beyond ~0.01% packet loss (8 MB throughput 73 Gbps at 10⁻⁷ loss → 2.5 Gbps at 10⁻³), and it burns cores polling ([eRPC §6.4, Table 4](https://www.usenix.org/conference/nsdi19/presentation/kalia)). Deployment: DPDK-bound NIC (removed from kernel control), hugepages, dedicated spinning cores, app rewritten to eRPC's event loop.

**Demikernel (SOSP'21):** a portable "datapath OS" (library OS) so the same app runs over DPDK, RDMA, or io_uring backends ([paper PDF](https://irenezhang.net/papers/demikernel-sosp21.pdf), [ACM DOI](https://dl.acm.org/doi/10.1145/3477132.3483569)). Numbers: 64 B echo RTT ~**5–7 µs** on its DPDK/RDMA stacks versus **~30 µs** for the same app on the Linux POSIX stack (same testbed); per-I/O overhead ~**250 ns** (RDMA backend) and **125–200 ns** per UDP/TCP packet (DPDK backend); a ported Redis gets **2x** throughput over RDMA and +20% over DPDK versus unmodified Redis ([Demikernel §7](https://irenezhang.net/papers/demikernel-sosp21.pdf)).

**Seastar:** the shared-nothing, core-per-shard C++ framework underlying ScyllaDB (each core owns its RAM, NIC queue, and data; message passing between cores; optional DPDK native stack). Its own benchmark: ~**7 M HTTP requests/sec on one 2-socket Xeon node** (2015-era hardware) ([seastar.io HTTP performance](https://seastar.io/http-performance/), [Seastar wiki](https://github.com/scylladb/seastar/wiki)). It's an application framework rather than a transport — the transport is still TCP (kernel or user-space).

**Context from the Homa side:** the ATC'21 paper places these stacks at **~1 M requests/sec/core (Shenango, RAMCloud) and ~10 M/core (eRPC) vs ~0.1 M/core for Homa/Linux**, with eRPC best-case latency 3.7 µs vs 15.1 µs for Homa/Linux — while cautioning that most bypass systems measure without realistic load balancing, mixed message sizes, or congestion control ([ATC'21 §7.1](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

## A5. Google's production stack: Snap/Pony Express, Swift, Falcon

**Snap / Pony Express (SOSP'19):** Google moved host networking into a user-space "microkernel-ish" service. Pony Express is its reliable transport with two-sided and one-sided (RDMA-like) ops ([SOSP'19 slides](https://www.sigops.org/s/conferences/sosp/2019/slides/marty.pdf), [The Morning Paper summary](https://blog.acolyer.org/2019/11/11/snap-networking/)). Numbers:

- **Up to 5 M one-sided remote memory ops/sec/core** in production workloads — 2x the hardware RDMA implementation it replaced ([Morning Paper on SOSP'19](https://blog.acolyer.org/2019/11/11/snap-networking/)).
- **38 Gbps using 1.05 cores vs kernel TCP's 22 Gbps using 1.2 cores** (up to 3x Gbps/core), with sub-10 µs one-way latencies; weekly fleet-wide releases with <200 ms "blackout" during transparent upgrade ([Morning Paper on SOSP'19](https://blog.acolyer.org/2019/11/11/snap-networking/)).
- Independent cross-check from the Homa side: Snap needs **7–14 cores to drive a 100 Gbps network at 80% bidirectional load** (vs ≥18 for Homa/Linux); with load balancing enabled its throughput/core drops 3.5–7x; and Snap reported **P99 short-message latency of 300–400 µs under high load** — 3–4x *worse* than Homa/Linux ([ATC'21 §7.1](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

**Swift (SIGCOMM'20):** the congestion control used with Snap: delay-based, targeting a per-hop delay budget, decomposing NIC-host vs fabric congestion. Result: **<50 µs tail latency for short RPCs at ~100 Gbps per server, near 100% load, with near-zero loss** in Google testbeds/datacenters ([Swift paper page](https://research.google/pubs/swift-delay-is-simple-and-effective-for-congestion-control-in-the-datacenter/), [PDF](https://saeed.github.io/CS8803_DNS_Spring2024/assets/swift_sigcomm20.pdf)).

**Falcon (2023→):** Google's answer to "the transport belongs in the NIC": a hardware transport IP block, first shipping in the **Intel IPU E2000**, opened through OCP in Oct 2023. It layers RDMA/NVMe ULPs over hardware connections with **Swift-derived delay-based congestion control, multipath via IPv6 flow labels, out-of-order-tolerant delivery**, drawing on Carousel/Snap/Swift/PLB/CSIG ([Google Cloud blog](https://cloud.google.com/blog/topics/systems/introducing-falcon-a-reliable-low-latency-hardware-transport), [OCP announcement coverage](https://convergedigest.com/ocp-summit-google-opens-falcon-for-hardware-transport/), [Netdev 0x18 talk](https://netdevconf.info/0x18/sessions/talk/introduction-to-falcon-reliable-transport.html)). The Netdev abstract claims an "order-of-magnitude improvement over software-only transports"; a full paper appeared at SIGCOMM 2025 ([ACM DOI](https://dl.acm.org/doi/10.1145/3718958.3754353), [summary](https://danglingpointers.substack.com/p/falcon-a-reliable-low-latency-hardware)). I could not verify independent microbenchmark numbers for Falcon (see Gaps).

## A6. QUIC — one paragraph on why it's the wrong tool

QUIC solves *Internet* problems — middleboxes, TLS handshake round trips, connection migration across NATs, per-stream loss independence over one path — none of which exist inside a datacenter, and it pays for them with mandatory encryption (even ACKs are encrypted) and user-space packet/ACK processing that cannot use the kernel TCP offload machinery. Measured costs: Fastly found their tuned quicly sustained **196 Mbps vs 466 Mbps for TLS-over-TCP** on the same box (CPU-bound, 2020) ([Fastly: QUIC vs TCP computational efficiency](https://www.fastly.com/blog/measuring-quic-vs-tcp-computational-efficiency)); a WWW 2024 study measured the QUIC+HTTP/3 stack delivering **up to 45.2% lower data rate than TCP+HTTP/2 on fast (~1 Gbps) links**, growing worse with bandwidth, root-caused to receiver-side processing and QUIC's user-space ACKs ([QUIC is not Quick Enough over Fast Internet, WWW'24](https://dl.acm.org/doi/10.1145/3589334.3645323), [arXiv version](https://arxiv.org/html/2310.09423v2)). For intra-datacenter RPC you would inherit TCP-like congestion control and stream semantics, plus extra CPU per message, while gaining features you don't need — which is why the datacenter alternatives above (Homa, SRD, Falcon, eRPC) all skip it.

## A7. Research peers, briefly (how they relate to Homa)

- **NDP (SIGCOMM'17, best paper):** switches keep tiny buffers and **trim overflowing packets to headers** so receivers see demand and **pull** data at line rate, with per-packet spraying — receiver-driven like Homa but requires switch changes; Homa's paper reports NDP giving >600 µs P99 one-way for 100 KB messages in a loaded 10 Gbps simulation, far above Homa ([NDP paper](https://dl.acm.org/doi/10.1145/3098822.3098825), [Homa SIGCOMM'18](https://arxiv.org/pdf/1803.09615)).
- **pHost (CoNEXT'15):** the earlier receiver-driven grant ("token") scheme on commodity fabric that Homa builds on — Homa's initial design granted one message at a time "like pHost", then generalised to overcommitment with priorities ([Homa SIGCOMM'18 §3.5](https://arxiv.org/pdf/1803.09615), [pHost via ATC'21 refs](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).
- **dcPIM (SIGCOMM'22):** ports classical switch-fabric Parallel Iterative Matching to the datacenter — senders/receivers run a few rounds of matching before sending long-flow data; claims near-optimal tail latency *and* utilization ([dcPIM paper](https://www.cs.cornell.edu/~ragarwal/pubs/dcpim.pdf)). Ousterhout's rebuttal: it compared against a hobbled "Homa+Aeolus", and dcPIM wins only for sub-BDP messages (P99 slowdown ~1.1 vs ~1.4) while Homa wins for longer ones ([Homa wiki critique of dcPIM](https://homa-transport.atlassian.net/wiki/spaces/HOMA/pages/1507461/A+Critique+of+dcPIM+Near-Optimal+Proactive+Datacenter+Transport)).
- **SIRD (NSDI'25):** "sender-informed, receiver-driven" — explicitly targets Homa's weak spot that receiver-driven scheduling handles the receiver downlink well but wastes buffers/bandwidth when *shared* links (ToR→spine) or sender uplinks are the bottleneck; schedules single-owner links, uses reactive control for shared ones; runs 100 Gbps in software on Caladan ([SIRD NSDI'25 page](https://www.usenix.org/conference/nsdi25/presentation/prasopoulos), [arXiv](https://arxiv.org/abs/2312.15403)).
- **Aeolus (SIGCOMM'20):** a "building block" for all proactive/receiver-driven transports (Homa, NDP, ExpressPass): the first-RTT *unscheduled* packets are the problem, so let switches **selectively drop only unscheduled packets** when congested; simulations claim e.g. 55.9% lower P99 completion for small flows when added to such protocols ([Aeolus paper PDF](https://www.cse.ust.hk/~kaichen/papers/aeolus-sigcomm20.pdf)). Aeolus's authors also produced the "Homa collapses with 200 KB/port buffers" result that Ousterhout contests (see B4) ([ATC'21 §5.5](https://www.usenix.org/system/files/atc21-ousterhout.pdf), [Homa wiki critique of Aeolus](https://homa-transport.atlassian.net/wiki/spaces/HOMA/pages/262185/A+Critique+of+Aeolus+A+Building+Block+for+Proactive+Transports+in+Datacenters)).

# Part B — Benchmarks and success metrics

## B1. How the Homa papers measure success

**Workloads W1–W5 (message-size distributions from real traces).** Ordered by mean message size; each benchmark draws message sizes from one distribution ([Homa SIGCOMM'18 Fig. 1](https://arxiv.org/pdf/1803.09615), [ATC'21 Table 3](https://www.usenix.org/system/files/atc21-ousterhout.pdf)):

| Workload | Source of trace | Mean size | How measured |
|---|---|---|---|
| W1 | Facebook **memcached** servers (statistical model of the "ETC" workload from Atikoglu et al.) | smallest (>70% of *bytes* in messages <1000 B) | app-level logs |
| W2 | **Search application at Google** | 433 B | app-level logs |
| W3 | **Aggregated: all applications in a Google datacenter** | 2,423 B | app-level logs |
| W4 | **Hadoop cluster at Facebook** | 60,175 B | packet captures |
| W5 | **Web-search workload used for DCTCP** (Alizadeh et al. 2010) | 385,315 B | packet captures |

Notes: W4/W5 sizes were *estimated* from packet captures using TCP-inactivity gaps, which the authors say **overestimates** message sizes; W1–W3 are true application-level message logs ([SIGCOMM'18 §2](https://arxiv.org/pdf/1803.09615)). The ATC'21 kernel evaluation drops W1 (behaves like W2) and truncates W4/W5 messages at 1 MB, Homa/Linux's max message size ([ATC'21 Table 3](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

**The slowdown metric.** For each RPC: `slowdown = measured end-to-end RTT ÷ best-possible RTT for a message of that size` (best-possible = same hardware, unloaded network; 1.0 is ideal). Reported at **P50 and P99**, plotted against message size with the x-axis scaled to the CDF of message counts so the common (small) sizes get visual weight ([SIGCOMM'18 §5.1](https://arxiv.org/pdf/1803.09615), [ATC'21 §5.2](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

**Load level.** SIGCOMM'18 runs at **80% network load** with Poisson open-loop arrivals (16 nodes, 10 GbE CloudLab, 8 clients + 8 servers, echo RPCs). ATC'21 runs its 40-node 25 GbE cluster at **80–90% of each protocol's maximum sustainable load** (e.g. 20 Gbps offered per host for W4/W5) — note this normalises load *per protocol*, not per link ([SIGCOMM'18 §5.1](https://arxiv.org/pdf/1803.09615), [ATC'21 Fig. 3 caption](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

**Simulation comparisons** (SIGCOMM'18 only): packet-level simulations against pFabric, pHost, PIAS, NDP; plus "maximum sustainable load" per protocol — Homa sustained higher loads than all four, e.g. overcommitment level 7 lifted W4 max load from 63% to 89% ([SIGCOMM'18 §5.2](https://arxiv.org/pdf/1803.09615)).

## B2. The kernel module's benchmark tooling

Described in the [HomaModule README](https://github.com/PlatformLab/HomaModule/blob/main/README.md) and used to generate the ATC'21 figures:

- **`cp_node`**: standalone client/server binary for latency and throughput tests between nodes (the workhorse; runs Homa or TCP traffic with configurable workload distributions).
- **`cp_vs_tcp`**: cluster-wide driver that runs Homa-vs-TCP/DCTCP comparisons; e.g. `cp_vs_tcp -n 10 -w w4 -b 20` = 10 nodes, W4 workload, 20 Gbps offered load (80% of a 25 Gbps network). It produced Figures 3 and 4 of the ATC'21 paper ([README](https://github.com/PlatformLab/HomaModule/blob/main/README.md)).
- **`cperf`** ("cluster performance"): the family of benchmark scripts around cp_node for reproducible cluster runs, in the repo since Dec 2019 ([README](https://github.com/PlatformLab/HomaModule/blob/main/README.md)).
- **Metrics**: Homa exports fine-grained counters at **`/proc/net/homa_metrics`**, with `util/metrics.py` to diff snapshots; there is also an internal timetrace facility used for the paper's tail-latency forensics ([README](https://github.com/PlatformLab/HomaModule/blob/main/README.md), [ATC'21 §5.2](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

## B3. What "success" should look like for Homa vs TCP

From the papers' own evaluation logic, a fair Homa-vs-TCP verdict needs all four of:

1. **Short-message tail latency under load** — P99 RTT (or slowdown) for the smallest ~20% of messages at ~80% load, not at idle. Reference points: Homa/Linux P99 for short messages 7–83x below DCTCP and 19–72x below TCP on 25 GbE; Homa's P99 was *below TCP/DCTCP's P50* for most sizes ([ATC'21 §5.2](https://www.usenix.org/system/files/atc21-ousterhout.pdf)). The README's shorthand: "Homa's 99th-percentile latency is usually better than TCP's *mean*" ([HomaModule README](https://github.com/PlatformLab/HomaModule/blob/main/README.md)).
2. **Messages/sec across many clients** — Homa/Linux reached **1.6 M small RPCs/sec per node vs 1.0 M for TCP** (60% higher, thanks to better NAPI batching: average 23 packets/batch vs none for TCP) ([ATC'21 Table 2, §5.1](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).
3. **Core efficiency (Gbps/core and cores-at-load)** — Homa/Linux is *not* good here: W2/W3 consume nearly all 20 hyperthreads without saturating 25 Gbps; extrapolated ≥18 cores to drive 100 Gbps at 80%; single-stream large-message throughput is only ~10 Gbps vs TCP's 20 Gbps (message interface can't pipeline the copy to userspace; equal to TCP once multiple RPCs are active) ([ATC'21 Table 4, §5.1, §6](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).
4. **Incast handling** — Homa's incast control (server-requested-many-responses case) handled **several thousand simultaneous RPCs without degradation**, and ~300 before packet-drop degradation with the mechanism off; switch buffer footprint measured at **≤8.5 KB per Gbps of switch bandwidth** (fits a Tomahawk-3's 7.5 KB/Gbps with tuning) ([SIGCOMM'18 §5.1](https://arxiv.org/pdf/1803.09615), [ATC'21 §5.5](https://www.usenix.org/system/files/atc21-ousterhout.pdf)). Caveat: the kernel module has **not implemented** the SIGCOMM paper's incast optimization ([HomaModule README](https://github.com/PlatformLab/HomaModule/blob/main/README.md)).

Also required for fairness (things critics check): give TCP many connections per node pair (the papers do — multiple client/server threads and sockets, settings chosen to maximise each protocol's performance), use jumbo-ish MTU (3000 B helped all protocols), and enable TSO/RSS ([ATC'21 §5](https://www.usenix.org/system/files/atc21-ousterhout.pdf); criticism angle in [ipSpace rebuttal](https://blog.ipspace.net/2023/01/data-center-tcp-replacement/)).

## B4. Published Homa-vs-TCP results — and the criticism

**ATC'21 headline results (40 nodes, 25 GbE, Linux 5.4.80, 2021)** ([paper](https://www.usenix.org/system/files/atc21-ousterhout.pdf)):

- Best-case 100 B RTT: **Homa 15.1 µs, TCP 23.4 µs, DCTCP 24.1 µs** (kernel-bypass floor on same hardware: 3.7 µs).
- P99 short-message latency at 80–90% load: **19–72x lower than TCP; 7–83x lower than DCTCP**. P50: 3.5–7.5x (TCP), 2.7–3.8x (DCTCP). No message size in any workload where TCP/DCTCP beat Homa.
- Stability: Homa short-message latency varies <2x over a 10x load change (DCTCP: 7x); Homa's P99 at full load is 40% *below* DCTCP's P99 at one-tenth the load.
- Where Homa's remaining tail comes from: **software congestion** — NAPI bursts of ≥100 µs from unrelated large messages occupying the app thread's core; TCP's tail instead comes from protocol-level HOL blocking and buffering. Conclusion: the P99 gap is protocol, not implementation quality.

**Where Homa's Linux implementation loses performance (the self-criticism in the paper is the sharpest published analysis):**

- Load balancing across cores multiplies overhead **2–3x**: best-case W4 short-RPC RTT is 15 µs single-core, but the **median** in the real cluster run is **~47 µs**, with only 1% under 30 µs — attributed to cache-coherence and scheduler/softirq hotspot effects ([ATC'21 §6](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).
- **~0.1 M RPCs/sec/core vs eRPC's 10 M**; 1.6 Mops/sec eats 18 of 20 hyperthreads doing no real work; round-trip software overhead 9.5 µs vs 5.6 µs of actual network time ([ATC'21 §6–7](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).
- The user-level RAMCloud Homa gets **P99 < 15 µs on W4 where Homa/Linux gets ~100 µs** (8x) — the kernel costs an order of magnitude ([ATC'21 §6](https://www.usenix.org/system/files/atc21-ousterhout.pdf); same numbers quoted in [LWN part 2](https://lwn.net/Articles/914030/)).
- Above the transport, **gRPC swamps everything**: gRPC-over-TCP RTT ~90 µs with two-thirds spent inside gRPC itself, so Homa's advantage shrinks unless the RPC framework is also fixed ([LWN part 2](https://lwn.net/Articles/914030/)).
- Paper's own conclusion: another **5–10x** is available only by eliminating software overheads — i.e., moving transports into NICs ([ATC'21 abstract, §7.2](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).

**External criticisms / replication-adjacent studies:**

- **Aeolus authors (Hai et al., SIGCOMM'20)** simulated Homa with statically partitioned 200 KB/port switch buffers and observed severe degradation from drops/timeouts. Ousterhout's measured rebuttal: with a modern *dynamic shared* buffer pool, Homa's actual peak occupancy was 246 KB (W2) to 8.5 MB (W5) in a 13 MB pool, no drops until the pool was squeezed to 7 MB, degradation at 6 MB — i.e. the criticism assumed the wrong buffer model, but Homa genuinely does need ~8.5 KB/Gbps of shared buffer ([ATC'21 §5.5](https://www.usenix.org/system/files/atc21-ousterhout.pdf), [Aeolus paper](https://www.cse.ust.hk/~kaichen/papers/aeolus-sigcomm20.pdf), [Homa wiki critique](https://homa-transport.atlassian.net/wiki/spaces/HOMA/pages/262185/A+Critique+of+Aeolus+A+Building+Block+for+Proactive+Transports+in+Datacenters)).
- **dcPIM (SIGCOMM'22)** and **SIRD (NSDI'25)** both position themselves as fixing Homa weaknesses (first-RTT unscheduled traffic and buffering; shared-bottleneck scheduling and overcommitment waste). SIRD notes the published Homa simulator doesn't implement the paper's incast optimization ([SIRD arXiv](https://arxiv.org/abs/2312.15403), [dcPIM paper](https://www.cs.cornell.edu/~ragarwal/pubs/dcpim.pdf)); Ousterhout maintains critique pages disputing dcPIM's comparison methodology ([Homa wiki](https://homa-transport.atlassian.net/wiki/spaces/HOMA/pages/1507461/A+Critique+of+dcPIM+Near-Optimal+Proactive+Datacenter+Transport)).
- **Operational/networking-community skepticism** ([ipSpace](https://blog.ipspace.net/2023/01/data-center-tcp-replacement/), [APNIC/Geoff Huston](https://blog.apnic.net/2023/05/22/death-of-tcp-predicted-news-at-11/)): the TCP comparisons under-provision connection counts vs real deployments; the position paper ignored RoCE/SRD/QUIC prior art; most datacenter TCP bytes are storage/bulk, where Homa has no advantage (and single-stream throughput is worse); Ousterhout posted a point-by-point response ([Homa wiki response](https://homa-transport.atlassian.net/wiki/spaces/HOMA/pages/19922945/)).
- **Kernel upstreaming as a live stress test:** the ~13 kLoC module has been through many netdev review rounds since Oct 2024 (v16 by Oct 2025, still unmerged; first mainline version expected to be neither functionally complete nor performant) — review friction has centred on API shape and staging, not on disproving the performance claims ([LWN: Begin upstreaming Homa](https://lwn.net/Articles/997858/), [lore.kernel.org thread](https://lore.kernel.org/netdev/CAGXJAmxKM5a95uhBwbmm1Z427=bGyZhcCUopycLMTEfc4dHnew@mail.gmail.com/T/), [Phoronix on the 2025 series](https://www.phoronix.com/news/Linux-Homa-2025-Patches)).
- I found **no independent third-party cluster replication** of the ATC'21 numbers on modern kernels/NICs (see Gaps).

## B5. What is genuinely "best-in-class" today (2026) for datacenter small-message RPC

Ranked by measured small-RPC latency/throughput per core, with deployment cost attached:

1. **Hardware transports / RDMA-class NICs** — raw verbs: ~1.7–2.9 µs median small-op latency (2019 measurements, [eRPC Table 2](https://www.usenix.org/conference/nsdi19/presentation/kalia)) and **330–370 M msgs/sec** on current ConnectX-7 silicon ([NVIDIA datasheet](https://www.nvidia.com/content/dam/en-zz/Solutions/networking/infiniband-adapters/infiniband-connectx7-data-sheet.pdf)). The direction of the industry: **AWS SRD in Nitro** ([IEEE Micro 2020](https://ieeexplore.ieee.org/document/9167399/)), **Google Falcon in Intel IPUs** ([SIGCOMM'25](https://dl.acm.org/doi/10.1145/3718958.3754353)), and the **Ultra Ethernet Consortium's UET 1.0 spec (June 11, 2025)** — a multipath, out-of-order-tolerant Ethernet transport ~75% derived from HPE Slingshot, backed by every major vendor ([UEC 1.0 announcement](https://ultraethernet.org/ultra-ethernet-consortium-uec-launches-specification-1-0-transforming-ethernet-for-ai-and-hpc-at-scale/), [Network World](https://www.networkworld.com/article/4006285/ultra-ethernet-consortium-publishes-1-0-specification-readies-ethernet-for-hpc-ai.html)). This is exactly the endgame the ATC'21 paper predicted ("move transport protocols to the NIC") ([ATC'21 §7.2](https://www.usenix.org/system/files/atc21-ousterhout.pdf)).
2. **Kernel-bypass software RPC (eRPC-style)** — still the per-core software record: **2.3 µs median, ~10 M RPCs/sec/core, 75 Gbps/core** on commodity lossy Ethernet ([eRPC NSDI'19](https://www.usenix.org/conference/nsdi19/presentation/kalia)) — at the price of DPDK NIC ownership, burnt polling cores, and no general OS integration. Production-hardened variant: Snap/Pony Express + Swift at Google (5 M ops/sec/core, <50 µs P99 short-RPC tails at ~100 Gbps/server) ([Morning Paper/SOSP'19](https://blog.acolyer.org/2019/11/11/snap-networking/), [Swift](https://research.google/pubs/swift-delay-is-simple-and-effective-for-congestion-control-in-the-datacenter/)).
3. **Kernel TCP (+DCTCP/BBR)** — remains the deployment default: ~20–25 µs small-RPC RTT, ~1 M RPCs/sec/node, ~42 Gbps/core bulk ([ATC'21](https://www.usenix.org/system/files/atc21-ousterhout.pdf), [SIGCOMM'21 host-stack study](https://www.cs.cornell.edu/~ragarwal/pubs/network-stack.pdf)). Nothing beats its compatibility.
4. **Homa/Linux's niche**: the only *general-purpose, in-kernel, plain-Ethernet* option with order-of-magnitude better short-message tails than TCP at high load — but per-core efficiency ~100x below eRPC, single-stream throughput below TCP, an RPC-shaped API apps must port to, and still not in mainline as of the v16 series (Oct 2025) ([ATC'21](https://www.usenix.org/system/files/atc21-ousterhout.pdf), [Phoronix](https://www.phoronix.com/news/Linux-Homa-2025-Patches), [HomaModule README](https://github.com/PlatformLab/HomaModule/blob/main/README.md)).

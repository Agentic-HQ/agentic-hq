# Project Philosophy & Origin Story

This doc contains some (rambling) thoughts on this project from the founder (Steve).  The intention is to give you a sense of why it was created and what my initial ideas on the direction of the project are.  It goes on quite long, so if you're short on time/interest - please skip it and read one of the [other less rambling docs](../README.md) :-)  

I created AHQ because I found it hard to get good results out of Claude Code when developing software.  I had to keep managing its context manually as it bloated with all the things we had been discussing that were no longer useful.  I had to keep manually correcting things it did wrong, and found the CLAUDE.md was being ignored.  To solve this I started including the rules I wanted followed only at the point they were relevant, and then also including them later in the process when the code was being reviewed.  I realised that to do this really well it was best done in lots of small, controlled steps.  I needed to constantly update and compress the information the Agent had in its context based on what it was doing at that exact point.  I used markdown files to store what the AI was learning and planning as it did the task, and then fed the relevant files into the next Agent as context for what they were going to do.  This worked well, but I didn't like having to manually clear the context, prompt the agent with the next Skill and then wait for it to fill its context by reading and understanding these files.

I wanted a way of automating the whole process.  I decided I wanted something very simple that I could use to chain together these Skills.  The simplest thing that I could think of was a very small TypeScript program, and so I wrote a framework that would allow me to chain together Claude Code Skill invocations, with the output from one command being a simple JSON file that could be used as the input for the next.

So this is what AHQ is: a framework that allows you to write and run a simple TypeScript program that chains together Skill invocations in Claude Code.

For many years, well before AI coding was available, I was fascinated by how to build really good software and I read many books on the subject and experimented with different techniques.  As this AHQ project progressed and I used AI to build it, I realised that a lot of these previous interests in software design were relevant to coding with AI.  Things like modularity, readability, cohesion, loose coupling and separation of concerns. Also the best ways to start with a simple feature or idea and explore the solution space.  And so I became interested in applying those techniques to building software with AI.  The two books that seem most relevant to these techniques are:
- [Modern Software Engineering: Doing What Works to Build Better Software Faster - Dave Farley](https://www.amazon.co.uk/Modern-Software-Engineering-Better-Faster/dp/B0BLY5XX2G)
- [A Philosophy of Software Design - John Ousterhout](https://www.amazon.co.uk/Philosophy-Software-Design-2nd/dp/173210221X)

I've watched lots of YouTube content on these books and am currently reading Dave's book.

In one of the videos Dave Farley asks whether maybe AI is our chance to get software engineering right.  I believe it is.  Using Agentic HQ (or some other automation tool) I think we can guide the human developer and the AI through a flexible, enjoyable and rich development experience which lets us "build better software faster".  The human can bring their unique skills to the process - skills that AI may not yet be great at, like simplicity, elegance, understandability.  AI can bring its unique skills - speed, ability to run through long boring checklists, instant knowledge of frameworks and libraries, troubleshooting, diagnosing bugs.

I also think there **is** actually a solution to the new problem of long, boring Code Reviews of AI written software - and it's not just using another AI tool to do the majority of the work in the Code Review.   The solution is to *Stop Reviewing* and *Start Collaborating*.  The AI can collaborate with the human to produce lots of documents and a final summary to show a detailed understanding of the code and the reasons for decisions made.  The human interacts with the AI and the documents to gain a deeper understanding of the code and to ensure the rules and conventions are being followed, and work has been done to prevent problems and bugs. Then the Code Review could become a 4-way (possibly real-time?) interaction between the human coder, the AI coder, an AI reviewer and a human reviewer.  Questions get asked in real time: "so why did you choose this technique and not that one?", "what kind of exception handling did you build in - show me please".  This is likely to be less boring than just reviewing raw code, and so could be more productive.  It could be done in "real time" or could be a delayed back and forth process using a Code Review tool, whichever the humans prefer.  But it's no longer just one poor reviewer trawling through hundreds of lines of newly generated AI generated code, feeling demotivated and overwhelmed.

UPDATE: After writing this I watched a video called [
Are Code Reviews Even Necessary?](https://www.youtube.com/watch?v=6AxuSfSe4BA) on the Modern Software Engineering YouTube Channel. In it the presenters argue that when pair programming is practiced really well, and people know what is expected of them in terms of style and following conventions and guidelines, then they find that Code Reviews are no longer necessary and code gets checked straight into trunk.  They keep asking the question "Why are you doing code reviews?".  I think part of the reason for this question is that whatever you are trying to fix at the Code Review stage can partly be pushed back into the actual coding process.  As an example here with AHQ - if you would do a code review to find problems with style guides not being met, then incorporate those style requirements into the rules using **during** coding rather than waiting for the code review.

Overall I think it's possible to make the process of making really high quality code more enjoyable and more productive by doing the things that produce the high quality interactively while coding, rather than in a review -> reject -> redo cycle at the end.

I'd like AHQ to be managed and built using all the brilliant ideas in the Modern Software Engineering book.  Harnessing all those quick feedback loops - and not just in coding, but in working out what feature to actually do next, and what direction to take this open source project in.  I'd like to explicitly follow each of the practices, to the point where AHQ could be provided as an exemplar of how the ideas in the book could be put into practice on a new open source project.

I can also see AHQ itself being used to create Workflows that encode all the brilliant ideas and techniques in Modern Software Engineering, so that when developers run the Workflows they learn about and are guided through the techniques while they develop their next feature, and the AI is also instructed in how to operate using the techniques.

Similarly there could be Workflows that encode and allow you to follow the great ideas in the A Philosophy of Software Design book, or any other methods of software engineering.

Recently I've also understood (from [Ben Davies in this video](https://youtu.be/xKOUge8Uf2c?si=bx0ICVIn1BB06PG0&t=4491)) the powerful idea that Skills can be written that actually *are* the final software product. (rather than being used to build software products).  Building a highly complex bit of AI powered software using Skills has its limits if you are running those Skills manually or trying to squash the whole system into a single Skill file, and so I can see AHQ being used to chain together and control the flow of those Skills and the data between them.  An example system Ben talked about building in his video was a YouTube data sync system involving a database, that he built using Skills rather than writing traditional deterministic software.  The output isn't always guaranteed to be the same, but if it does the job really well 99% of the time and is easily verifiable - that's fine.  He said that writing the system like this, as a series of Skills for the AI to follow, was much quicker and easier than creating traditional software, because it leaves the details of how to do stuff to the AI to work out.  This is a very interesting new way of looking at how some of the systems we write and use could be implemented.

So, now you have a better idea of where I'm coming from and some of my ideas related to the project.  I want the direction of AHQ (Agentic HQ) to be **open** and based on what contributors want to build and on user feedback and real use cases that solve real problems for people.  

The key seems to be understanding how much I *don't* know and opening myself and the project up to what people really want to build and what people really want to use it for.  

So, on that note, over to you... :-)
